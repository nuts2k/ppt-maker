## 四、发现的缺陷

### 缺陷 ①：零建立时报告落了盘，但没有任何地方告诉用户它在哪

**现象**：把一份全部非 16:9 的 PDF 抽进**已存在**的 deck，报告照常写入
`<deck>/extractions/`，里面逐页写着尺寸与原因；而用户在终端只看到一句
`错误：PDF 中没有可用于建立页面的 16:9 页：no-wide.pdf（跳过 2 页）`——
**没有页号、没有尺寸、没有原因、没有报告路径**。桌面端同理：活动日志那一行
没有「查看报告」按钮，磁盘上那份报告在界面里**完全不可达**。

**复现**：

```bash
# 先有一个 deck（本走查用 a6-mixed-2026-08-02）
node apps/cli/dist/index.js deck extract --pdf ~/test/no-wide.pdf --deck ~/test/a6-mixed-2026-08-02
echo $?          # 1
ls ~/test/a6-mixed-2026-08-02/extractions/   # 报告确实新写了一份
```

**根因**：

- `apps/cli/src/pdf/extract.ts:304-327` —— `created.length === 0` 时先写报告
  （追加路径，`temporaryDeck === null`），随后 `throw new FoundationError(...)`。
  `details` 里只带 `{ pageNumber, code }`，**不带尺寸、不带 `reason.message`、不带 `reportPath`**。
- `apps/cli/src/index.ts:432-434` —— `formatExtractionReport(result.report)` 与
  `result.reportPath` 的打印在**成功路径之后**，抛错就整段跳过。
- 顶层 catch（`apps/cli/src/index.ts:705-708`）只打印 `error.message`。
- `apps/desktop/src/main/runner/source-task-runner.ts:88` 的 `recordFailure`
  （定义在 `:234-244`）**没有 `reportPath` 参数**，写进活动日志的记录因此不带该字段，
  `ActivityPanel.tsx:154` 的按钮条件 `reportPath !== undefined` 不成立。

这正是 `silent-failure-thinking-guide.md` 那两条自查的同型情况：
「这个返回值有几种结局？每一种都有人渲染吗？」——抽取有第三种结局
（**追加路径 + 零建立**：报告有、页没有、命令失败），它掉进了
「成功才打印报告 / 失败只打印一句话」的缝里；以及「新写盘的东西，靠什么让界面跟上？」

**建议修法**（未实施）：

1. `extract.ts` 抛错前把已算出的 `reportRelativePath` 与整份 `report` 放进
   `FoundationError.details`（追加路径下报告已落盘，新建路径下没落盘就只放 report 本身）。
2. `index.ts` 的 `deck extract` action 包一层 try/catch：捕获后先
   `process.stderr.write(formatExtractionReport(report))` 再重新抛出，
   让逐页原因在失败时也能看到；有 `reportPath` 时一并打印。
3. `source-task-runner.ts` 的 `recordFailure` 增加可选 `reportPath` 并在 `:88` 透传，
   活动日志失败行随之长出「查看报告」按钮。

**影响 A6 的判定吗**：不影响。A6 的「不整体失败」只覆盖混合宽高比，
而混合场景（`EXIT=0`）报告路径是正常打印的。这条是相邻场景的可发现性缺口。

### 缺陷 ②：`hasExtractableText` 的页级可见性只存在于注释里

**现象**：`apps/desktop/src/renderer/lib/extraction-report-view.ts:109-110` 写着

> `hasExtractableText` 在这里只是抽取当时的观测值。页级的权威来源是每页
> `manifest.source`（重抽后也不会失真），**页面详情走那条**，不靠这份报告。

但桌面端**没有任何组件读 `source.hasExtractableText`**。全仓 grep，
`apps/desktop/` 下这个标识符只出现在上面那段注释和 `:117` 的格式化里；
IPC 契约 `apps/desktop/src/main/ipc/channels.ts:35` 的 `DeckStatusSlide` 只带
`sourceKind`（`imported` / `extracted` / `generated`），`hasExtractableText`
根本没过 IPC 边界。逐页来源展示（`apps/desktop/src/renderer/lib/source-view.ts`
的 `sourceBadgeLabel`）只有「抽取」两个字。

**后果**：探测结果在界面上**只有抽取报告面板一条路径**，而那条路径依赖桌面端自己的
活动日志（userData、按 deckId、CLI 不写）。因此：

- **CLI 建立的 deck，在桌面端没有任何入口能看到这个字段**（本走查的三个 deck 都是这种）；
- 即便是桌面端建的，一旦活动日志被清理，报告文件还在磁盘上却再也点不开；
- 「重抽后也不会失真」这个注释承诺的性质（页级权威源）没有任何界面在兑现。

**根因定位**：

- 承诺方：`apps/desktop/src/renderer/lib/extraction-report-view.ts:109-110`（注释）
- 缺口处：`apps/desktop/src/main/ipc/channels.ts:35`（IPC 只截到 `sourceKind`）、
  `apps/cli/src/deck/status.ts:199`（CLI `deckStatus` 同样只回 `source.kind`）
- 消费侧：`apps/desktop/src/renderer/lib/source-view.ts`（只有 kind 文案）

**建议修法**（未实施，二选一）：

- **A（补能力）**：`DeckStatusSlide` 增 `hasExtractableText: boolean | null`
  （非 `extracted` 页为 `null`），`source-view.ts` 加一句详情文案，
  在单页详情 / 审片视图里显示。这样注释所说的「页面详情走那条」才成立，
  且不再依赖活动日志。
- **B（改注释）**：把 `:109-110` 改成实情——页级权威源在 manifest 里，
  但**当前界面不读**，可见性依赖抽取报告面板。

倾向 A：A5 的验收原文是「每页的可提取文本探测结果落盘且**在界面可见**」，
