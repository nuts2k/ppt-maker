## 发现的问题

### D1（缺陷，低严重度）换源归档改了资产 id，但没同步 attempt 的 `assetIds`，指向被下一代顶掉

**现象**：`slides/page-02/manifest.json` 里，`accept-source-001` 这次 attempt 的
`assetIds` 是 `["asset-source-acceptance"]`，而 manifest 中 id 为 `asset-source-acceptance`
的那条资产 `attemptId` 是 **`accept-source-002`**、路径是 `stages/source/accepted.json`
（第二次确认的记录）。第一次确认的那份被归档成
`asset-source-acceptance-archived-init-002` → `stages/source/archived/init-002/accepted.json`，
**没有任何 attempt 引用它**。

即：顺着「第一次确认」这次 attempt 往下追，追到的是**第二次确认**的文件。

**复现**（触发条件是 generated 页的常规循环：确认 → 重新生成 → 再确认）：

```bash
cd ~/test/a713-spec-2026-08-02 && python3 - <<'PY'
import json,glob
for p in sorted(glob.glob('slides/*/manifest.json')):
    m=json.load(open(p)); byid={a['id']:a for a in m['assets']}
    for at in m['attempts']:
        for aid in at['assetIds']:
            a=byid.get(aid)
            if a and a['attemptId']!=at['id']:
                print(f"{p} attempt={at['id']} → 资产 {aid} 的 attemptId 实为 {a['attemptId']}  path={a['path']}")
PY
# slides/page-02/manifest.json attempt=accept-source-001 → 资产 asset-source-acceptance 的 attemptId 实为 accept-source-002  path=stages/source/accepted.json
```

**根因**：`apps/cli/src/slide/replace-source.ts:172-178` —— `archiveArtifacts` 在
`renameId: true` 时把资产 id 改成 `${asset.id}-archived-${initAttemptId}`，但只重建了
`assets` 数组；同文件 `:390` 写 manifest 时 `attempts: [...workspace.manifest.attempts, …]`
把旧 attempt **原样透传**，其 `assetIds` 里的旧 id 没跟着改。旧 id 随后被下一次
`accept-source` 以固定 id 重新占用（`accept-source.ts` 写 `asset-source-acceptance`），
于是从错指变成**指向另一代产物**。同一路径也适用于 `review_validation`（`renameId: true`）。

**影响**：目前全仓**没有任何消费方**读 `attempt.assetIds`（grep 只命中 schema 与写入侧；
`SlideWorkspaceManifestSchema` 也不校验它引用的 id 存在），所以没有可见症状。
但它是一条与事实相反的落盘记录，正是〈静默失败诊断指南〉「宁可不写，不写假的」那一类，
将来任何按 attempt 汇总产物的功能（报告、审计、成本归集）第一次读它就会读到错的。
**不影响 A7**：生成产物的资产 id 自带 attempt 后缀（`asset-init-002-*`），从不改名。

**建议修法**：`archiveArtifacts` 返回一份 `旧 id → 新 id` 的映射，
写 manifest 时对既有 `attempts` 做一次 `assetIds.map(id => renamed.get(id) ?? id)`。
测试锁死「归档后遍历所有 attempt 的 assetIds，每个都能在 assets 里找到且 `attemptId` 自洽」
——这条不变量正好也是上面那段复现脚本。

### D2（缺陷，低严重度）报告里的 `providerCalls` 不带 `attemptId`，多代生成无法区分

`apps/cli/src/report/run.ts:188-205` 按**裸 role** 收集全部 `provider_record`
（这里是有意的，成本要算全部历史调用），但只写入 `stage / model / requestId / durationMs / usage`。
page-02 这种跑过两次生成的页，报告里会出现两条 `stage: "init"`，
`requestId` 都是 `null`、model 相同，**只有 durationMs 能勉强区分**，无法回答
「哪一条对应当前这张图」。A7 要求的是「从**工作区**追溯」，工作区侧完好（见上），
故不判 A7 不通过；但报告是给人看的最终交付物，这里丢了锚点。
建议：`providerCalls[]` 补一个 `attemptId`（`ProviderCallRecord.id` 就是 `provider-<attemptId>`，
或直接取承载它的资产的 `attemptId`），并在 `report-contracts.ts:69` 一并加字段。

### O1（观察）「成本」只有 token 用量，没有金额

全仓 grep 无任何单价 / 金额 / cost 字段（只有 `source-contracts.ts:65-66` 的注释提到「成本」）。
A7 原文写的是「用量成本」，工作区给到的是 token 明细 + 耗时，够做用量归集，
但要换算成钱得另外查价目表。这与 design §2「成本与用量不重复存放，由 `ProviderCallRecord` 持有」
一致，**不算偏离设计**，只是「成本」二字在验收标准里比实现更强。
若要收口，建议在 ROADMAP/PRD 把措辞改成「用量」，或另立一条「按价目表折算金额」的能力。

### O2（观察）`requestId` 恒为 `null`，无法与 provider 侧对账

四页八次调用全部 `requestId: null`。**不是代码缺陷**：
`apps/cli/src/providers/openai-image.ts:186-189` 走 `client.images.generate(params).withResponse()`
如实透传 SDK 的 `request_id`（来自 `x-request-id` 响应头），本机 `.env` 的
`OPENAI_BASE_URL` 指向第三方代理（`https://dtcpa.nuts2k.eu.org/v1`），该代理未回传这个头。
后果：出账单争议或要向上游追一次具体调用时，工作区里没有可对账的 id；
`model` 也只有名字、没有服务端快照版本，`promptVersion` 是本仓库自己的版本轴。
换直连官方 endpoint 时该值应自动出现——建议主会话在 A12 的那次真实生成里顺手看一眼，
若直连仍为 null 才需要查代码。

### O3（观察）生成参数在同一文件里拼了两遍，键名写法还不同

`apps/cli/src/deck/generate-page.ts:158-163`（写进 `GeneratedSource.parameters`，驼峰
`outputFormat`）与 `:207-212`（写进 `ProviderCallRecord.parameters`，蛇形 `output_format`）
各拼一份。当前两处的值同源于 `CLEAN_PLATE_SIZE / CLEAN_PLATE_QUALITY / CLEAN_PLATE_OUTPUT_FORMAT`
常量，所以还不会漂移；但「加一个生成参数」时极易只改一处，而两份记录都没人比对，
漂移是静默的。属规范里「有没有一份值在两处各存了一份」那一条的轻量版。
建议：抽一个 `buildGenerationParameters()` 返回蛇形一份，驼峰那份由它映射，或干脆两处同形。
