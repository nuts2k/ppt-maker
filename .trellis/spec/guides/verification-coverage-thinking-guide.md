# 验收覆盖思考指南

> **用途**：动手写验收标准、设计 fixture、或判断「这条验收标准能不能算通过」时，用它检查覆盖形状有没有漏。
>
> 核心问题只有一个：**你的验收止步于哪里，缺陷就藏在哪之后。**

---

## 为什么需要这份指南

M5 子任务①「页面来源契约」的 B1–B10 曾在自动化测试全绿（550 项）+ 一次两页小 deck 走查后判为通过。随后在**真实 deck**（跑完十阶段的 `ppttest-2026-07-25`）上补跑含云调用的完整链路，一次性又暴露四个缺陷，其中三个是必现的——**任何跑完正常链路的页都换不了源，换了源的页跑不过 mask**。

这四个缺陷没有一个是「代码写错了」那种低级错误，它们全部藏在验收覆盖的形状之外：

| 缺陷 | 为什么之前没发现 |
|---|---|
| 换源归档重复 `rename` 必 ENOENT | fixture 每页只有**一条** `text_review`；真实页跑完链路后 `review` 与 `assist-review` 各写过一次，有**两条指向同一路径** |
| 换源后跑 mask 必被误拦 | 自动化测试**止于「换源成功」**，没有继续跑下游 |
| `source_acceptance` 未归档 | 走查造的页从没「先人工确认、再换源」过 |
| `deck status` 指着 completed 的阶段报失败 | 只在「正常推进」的页上看过输出，没在换源后的页上看 |

**共同特征：不是判据写错了，是判据从没在会出问题的那种形态上运行过。**

## 动手前问自己四个问题

### 1. 我的 fixture 长得像真实产物吗？

最危险的 fixture 是**恰好只有一条**的那种——裸 `find` 在它上面碰巧也对。

- 真实的页跑完链路后，同一个 `role` 有几条资产？（`text_review` 4 条、`clean_plate` 3 条、`provider_record` 7 条都是常态）
- 我造的这条是不是「刚初始化」的形态，而缺陷只在「跑过很多轮」的形态上出现？
- **加前置断言**：先断言 fixture 确实是那种危险形态（该 role 恰好 N 条、第 0 条是归档路径），否则用例可能什么都没覆盖。

参见《跨层契约》的〈多代资产与「当前产物」选取契约〉。

### 2. 我跑到哪一步就停了？

**「操作成功」不等于「操作之后还能继续」。**

涉及会产生新一代产物的操作（换源、重跑、失效、归档），验收形状必须是：

```
跑完完整链路 → 执行该操作 → 继续跑下游到底
```

只验到中间那一步，等于只证明了「没有立刻炸」。

### 3. 人工点我是怎么过的？

走查里代替人工步骤（脚本批量标记复核、CLI 代记录验收）是可以的，但：

- **必须如实记进验收记录**——把「未实际人工检查」写进 `--note`，让磁盘上的记录本身诚实
- 要分清哪些结论**不受**代劳影响（链路连通性、零迁移、人工点数量），哪些**受**影响（复核质量、视觉效果）
- 绕过产品写路径直接改磁盘会被完整性守卫拦下（这是守卫在正常工作），改完要走一遍产品的校验命令

### 4. 我是在真实数据上验的，还是在自己造的数据上验的？

自己造的数据带着自己的假设。真实历史数据（M3/M4 时代的旧 deck、跑过多轮的页）会带来你想不到的形态。

**涉及兼容性、迁移、历史数据的验收标准，不接受仅凭 fixture 推断。**

### 5. 标准说「报告能看出 X」，我是不是只验到「磁盘上存着 X」？

这两件事差着一整个消费端。M5 的 A10 要求「报告能区分人工确认与按来源自动放行」，磁盘层区分得干干净净（`provider` 一个 `auto-source-trust` 一个 `developer`、`assetIds` 一空一有、`accepted.json` 一无一有），**但全仓没有任何一处读它**——`deck status`、`report.json`、桌面端界面三处都看不出差别。翻磁盘 JSON 验完就勾，这条标准会被假阳性放过去。

- 标准里出现「报告」「界面」「能看出」「可见」这类词时，**验收动作必须落在那个报告或那个界面上**，不能落在磁盘上。
- 反过来也成立：只在界面上看到了，不等于磁盘记录是对的（A10 的另一半要的正是「磁盘上**没有** `accepted.json`」）。**两头都要验，各验各的。**
- 一个快速自查：`grep` 那个标记的产生端与消费端。**只有产生端，就是还没做完。**

### 6. 我这条「零变化」判据，是不是被别的东西污染了？

「其它页完全不受影响」这类标准靠的是目录 shasum 前后一致。但如果**编排本身不幂等**，基线就是流沙——M5 实测 `deck run` 对一份全完成的 deck 每跑一次就重写 11 页的 `report.json`（新 `generatedAt`）与 `validation.json`（新 `checkedAt`），于是任何「跑一遍再比对」的判据都会看到满屏 diff。

- 打基线快照前，先确认**空跑一次是零 diff 的**；不是的话，先去修那个不幂等，别在流沙上验收。
- 只比 `deck status` 的字段不够，要比每页目录的 shasum；但也别只比 shasum——状态与产物两样都要。

## 判断一条验收标准能否勾掉

| 情形 | 结论 |
|---|---|
| 自动化测试全绿，但没在真实历史数据上跑过 | 兼容类标准**不能**勾 |
| 操作本身成功，但没跑下游 | 涉及新一代产物的标准**不能**勾 |
| 人工步骤被代劳，且结论依赖人工质量 | 标记 `[~]` 并写明代劳处，不能勾 `[x]` |
| 人工步骤被代劳，但结论只依赖链路连通性 | 可以勾，但必须写明代劳处 |
| 需要真机 / 原生对话框 / 外部权限确认 | 必须由人亲眼确认后才能勾（本机无屏幕录制与辅助访问权限，AI 截不到也点不了原生框） |
| 标准说「报告/界面能看出 X」，但只验到磁盘上存着 X | **不能**勾——差一个消费端，见问题 5 |
| 「其它页零变化」类标准，但没先确认空跑是零 diff | **不能**勾——基线可能是流沙，见问题 6 |

## 走查的组织方式

一轮集成验收往往有十几条标准要过，串行走会很慢。M5 阶段三的做法可以复用：

- **按条目切分，每组一份独立的 deck 副本**，并行跑。副本之间不共享路径，互不干扰；基线 deck 单独留一份不动，随时可回头对照。
- **单实例的东西不能并行**：桌面端只能起一个（两个 Electron 会抢调试端口，表现为「补丁打在 A、界面跑在 B」），所以「界面上是什么样」这一半统一由一个人取证。
- **走查代理只走查、不改产品代码**。发现的缺陷写进记录（现象 → 复现命令 → 根因定位到文件:行 → 建议修法），修复串行做——多个代理同时改同一批文件，合并冲突的代价远大于并行省下的时间。
- **走查记录里的误判要当场更正**，不能留着。M5 有一条初稿写「活动日志那行不可点、报告关掉就回不去」，实测是**折叠状态**下看的底部状态条，展开后本来就有「查看报告」。错误结论留在记录里，比没有记录更糟。
