# 静默失败诊断指南

> **用途**：当用户报告「点了没反应」「不知道跑没跑」「卡住了」，或者反过来——**界面说成功了但产物不对**时，用它定位真正的失败点。
>
> 两类症状根子相同：**界面显示的状态不是磁盘上的状态**。第一类是界面比磁盘少说了（下方「诊断顺序」），第二类是界面比磁盘多说了（下方「第二类」）。

---

## 为什么需要这份指南

M4 端到端走查一次性暴露 7 个缺陷，其中 5 个的用户可见表现**完全相同**——点击后界面毫无变化。但根因分散在四个不同层次：

| 表现 | 真实根因 | 所在层 |
|---|---|---|
| 单页复核打开后空白 | 读取路径少一层目录，`catch { return null }` 吞掉 | main IPC |
| 「运行此页」纹丝不动 | 续跑起点计算死锁，永不回头校验 | main 编排 |
| 验收界面说缺产物 | 产物齐全，store 是进页那一刻的快照 | renderer 状态 |
| 「重跑」点 6 次无反应 | 阶段仍是 completed，被幂等跳过（毫秒空转） | CLI 编排 |
| report「运行没反馈」 | 跑成功了但不写状态，UI 永远显示未完成 | CLI 落库 |

**共同特征：失败或无效被静默吞掉，没有任何一层发出声音。** 凭猜测逐层排查代价极高，必须靠证据。

---

## 诊断顺序（严格按此顺序，不要跳步）

### 第 1 步：先分清「没跑」还是「跑了但没效果」

**看活动日志的时间戳**（`~/Library/Application Support/@ppt-maker/desktop/activity/*.jsonl`）：

```bash
tail -30 ~/Library/Application\ Support/@ppt-maker/desktop/activity/*.jsonl | python3 -c "
import sys,json
for line in sys.stdin:
    if line.strip().startswith('{'):
        d=json.loads(line)
        print(f\"{d['at'][11:19]}  {d['kind']:14} {d.get('stage') or '-':16} {d['result']:8} {d.get('detail','')}\")
"
```

| 日志特征 | 结论 |
|---|---|
| 完全没有 `run-start` | 事件没发出——查 UI 事件绑定、`disabled` 条件、前置 return |
| `run-start → page-done` 在**同一秒内**，且**没有任何 `stage-start`** | **所有阶段被跳过**——查阶段状态是否还是 `completed`（见下方「幂等跳过」） |
| 有 `stage-start` 但无后续 | 真的卡在某阶段——查该阶段的外部调用与超时 |
| `stage-complete ... success` 却反复出现同一阶段 | **跑成功了但状态没落库**——查该阶段收尾是否写了 `stages`/`attempts` |

> 毫秒级完成 ≠ 成功。它多半意味着什么都没做。

### 第 2 步：对照磁盘产物与界面显示

```bash
# 阶段状态
python3 -c "
import json
for s in json.load(open('<workspace>/manifest.json'))['stages']:
    print(f\"  {s['stage']:16} {s['status']}\")
"
# 产物是否真的在
ls <workspace>/stages/<stage>/
```

| 磁盘 | 界面 | 结论 |
|---|---|---|
| 产物齐全 | 说缺产物 | **读取侧问题**——路径错、快照过期、asset role 不匹配 |
| 产物缺失 | 说已完成 | 落库与实际不符——查写盘顺序 |
| 状态 pending | 日志说成功 | 收尾漏写状态 |

### 第 3 步：确认「重跑」的语义是否真的成立

只要阶段状态还是 `completed`，`run-from` 的守卫与 `isStageReusable` 会**双双放行复用**，任何重跑都被静默跳过。显式重跑必须先调 `invalidateSlideStage` 标 `stale`。

详见 [跨层契约 · 阶段落库与强制重跑](../backend/contracts.md)。

## 第二类：界面有反馈，但反馈是假的

> 2026-07-27 复核链路走查暴露 6 个缺陷，其中 **4 个属于这一类**——用户点了，界面给了正反馈，实际什么都没发生，或者写下的记录与事实相反。它比「点了没反应」更危险：没反应用户会重试，假成功用户会继续往下走。

| 表现 | 真实根因 | 归属 |
|---|---|---|
| 点阶段轨道的「复核校验」，界面切回复核视图并提示成功，manifest 一字未改 | 瞬态阶段不在持久阶段集合里，失效函数匹配不到，**静默返回空数组**；随后 run 因全部仍 completed 被整段跳过 | 跨进程类型两侧各标各的，中间隔着无运行时校验的 IPC |
| 磁盘上六个阶段已转 `stale`，阶段轨道却一片绿 | 派生视图是「耐久层打底、会话层覆盖」，上一轮 run 结束时**刻意保留**了会话层结果，不清就永远盖住新写入的 stale | renderer 状态分层 |
| 验收后 manifest 写下「人工确认尺寸正确」，而同页自动检查是尺寸不符 | 合并两道验收后界面已无勾选框，仍沿用一组恒 `true` 的默认清单 | 语义变更后遗留的默认值 |
| 人工确认一个块，叫「待确认」的计数纹丝不动 | 操作确实生效了；徽标显示的是**分区总数**而非未复核数，且两处各写一份 filter 口径不一 | 计数口径漂移 |

### 全局单例的事件订阅：「一处都没挂」和「挂了两处」都是静默的

M5 ④ 加 `deck:source-task-progress` 这条新 IPC 事件通道时，**两种都实际发生过**：

- **一处都没挂**（`useSourceTaskStore.subscribe()` 忘了调）：进度事件全部落地无人接，
  界面永远停在「执行中」，任务其实早跑完了。**不报错**——没人订阅的事件不会抱怨。
- **随后被两处同时挂**：每个事件处理两遍。进度条这类幂等赋值看不出异常，
  一旦事件带累加语义（计数 +1、追加一条日志）就会翻倍，而翻倍同样不报错。

判据：**新增一条 IPC 事件通道时，订阅点必须唯一且在应用根**，并在另一个「看起来也该
订阅」的位置（多为该 store 自己、或消费它的第一个组件）留一条反向注释写明订阅在哪。
两个失败方向都不产生任何错误信号，只能靠「唯一订阅点」这条结构约束来防。

同一条约定在既有代码里已经写死过一次：`activity-store` 顶部注明「本 store **不订阅任何
IPC**，`onDeckRunProgress` 的订阅统一由 run-store 持有」——那句注释就是这条判据的先例。

### 三条判据

1. **凡是「失效 / 作废 / 重做」的入口，返回空集合必须是可见的**。失效是强制重做的唯一入口，静默失败一定退化成「点了没反应」。未知或无法处理的目标应当**抛错**，不要返回空数组。
2. **会话层覆盖耐久层时，谁写入谁负责清理**。凡是「不重跑的失效路径」都要显式清会话层——重跑路径侥幸不出问题，只是因为新事件会立刻覆盖旧值。
3. **宁可不写，不写假的**。没有真实人工动作支撑的字段，留空比填默认值好：空值如实表示「这步没做」，默认 `true` 会在记录里留下与事实相反的证据。

### 定位手法

对照磁盘与界面（见上方第 2 步）之外，这一类还要多问一句：**这个「成功」有没有对应的磁盘写入？** 具体做法是记下操作前后的 `manifest.json`：

```bash
cp <workspace>/manifest.json /tmp/before.json   # 点击前
diff <(python3 -m json.tool /tmp/before.json) <(python3 -m json.tool <workspace>/manifest.json)
```

**diff 为空 = 这次操作没有任何持久后果**，无论界面说了什么。

## 编码期的预防清单

写新阶段或新交互入口时逐条自查：

- [ ] **`catch` 里是否直接吞掉了错误？** `catch { return null }` 会把「文件不存在」和「路径写错」变成同一个结果。至少要能区分。
- [ ] **阶段收尾是否同时写了 `assets` / `stages` / `attempts`？** 漏写 `stages` 的表现就是「跑了但界面没变化」。
- [ ] **新加的「重跑」入口是否需要先失效？** 显式指定起点 = 强制重做，必须失效；无参续跑 = 断点续跑，不该失效。
- [ ] **renderer 的数据是一次性加载还是跟随事件更新？** 如果闸门走事件、数据走进页快照，两者必然不同步。
- [ ] **测试断言落在哪里？** 只断言函数返回值不够——**必须断言落库后的持久状态**。缺陷 6 的 5 个既有用例全部只检查返回内容，因而完全没发现状态从未写入。
- [ ] **这个成功提示背后有磁盘写入吗？** 只要提示语与写盘不是同一条链路，就有说假话的空间。
- [ ] **界面上同一个数字有几处在算？** 两处各写一份 filter 必然漂移；口径收敛到一个纯函数，消费方一律调它。
- [ ] **新增瞬态阶段（不写 manifest 的阶段）了吗？** 它必须配一个可失效的持久替身，并有测试锁定「执行序列里每个阶段都能解析出失效目标」。
- [ ] **界面上有哪份数据是只读的？它凭什么被认为不需要改？** 只读展示是一句隐含断言：「这份数据是对的」。凡是断言由**启发式**给出（双源一致、置信度高、自动检查通过），就必须留人工推翻的入口——启发式会错，而只读会让它的错**静默**通过。2026-07-30 实测：「双源一致」被当成「无需改动」，但 OCR 与 AI 助手完全可能同错（己/已、末/未、专有名词、品牌名），同错即只读，错字一路进最终 PPTX，用户没有任何界面手段拦截。入口不必常驻——点击转编辑既留了通道，又不把 155 个输入框铺满列表。
- [ ] **有没有一份值，在两处各存了一份？如果两边写法不同，机器与肉眼都发现不了漂移。** 2026-07-31 实测：画布标注的线宽必须按 `scale` 逐帧反算，只能写 inline style，`border` / `box-shadow` 是宽度与颜色一体的简写，颜色因此也落进 JS，用不上 Tailwind 类。于是 7 个颜色以 hex 镜像了 `tailwind.config.ts` 的令牌，注释写着「改令牌时这里要一起改」——**人肉同步，迟早漏**，而且失效是静默的：改了配置里的 `proof`，画布上的红纹丝不动，没有任何东西会报错。解法有两层：① 让两边成为**可逐字比对的同一串字符**（把 hex 改成与 palette 一模一样的 oklch 串，只把 `<alpha-value>` 换成实际值），断言直接 `toBe`；② **配一条反向锁**——只比对模块里的值是不够的，后来人绕过模块在组件里就地写死 `#be222a`，正向锁照样全绿。反向锁读源文件断言「这个文件里不得出现 hex / rgba」。两条锁缺一不可。

- [ ] **这个返回值有几种结局？每一种都有人渲染吗？** 一个结果类型只要多出**第三种**结局，它就极可能掉进既有两套呈现的缝里，而缝里的东西是静默的。2026-08-02 走查实测：建页任务的结果有「成功 / 抛异常 / `accepted: false` 被互斥挡下」三种，完成面板与抽取报告都只认 `accepted`，错误条只认抛出来的异常，于是流水线执行中点「追加页面」，main 如实回了理由，界面上**模态一关、一动不动**——理由静静躺在 store 里，没有任何组件读它。编排层甚至写着「被互斥挡下不是丢弃，它要照常报给用户」，意图在、呈现不在。判据：**把返回类型的取值域列全，逐个问「谁把它画出来」**；答不上来的那一支就是静默分支。别用「反正 main 会记日志」搪塞——用户不看 jsonl。

- [ ] **新写盘的东西，靠什么让界面跟上？** 同一轮里新加一条「写磁盘」的链路时，问一句 *现有的哪个刷新会覆盖它？* 2026-08-02 走查实测：④ 新增的建页任务在收尾时写活动日志，但**追加**场景不换 `deckPath`，没有任何 effect 会重载日志——抽取报告一关就再也找不回来，而磁盘上那条记录一直在。既有的流水线路径之所以没事，是因为 run-store 在 `run-done` 里显式重拉了一次；新链路照抄了「写」，没照抄「拉」。

- [ ] **某个动作的入口，长在一个会消失的容器里吗？** 页面/面板/分区一旦按「还没做完」显示，做完之后它连同里面的动作一起消失。问一句：*这个动作在容器消失后还有别的入口吗？* 没有就是能力凭空丢失，见 [State Management · 一个判据兼职两件事](../frontend/state-management.md)。

- [ ] **调的这个系统 API，「自适应」是双向的吗？** 名字里带 fit / adapt / preserveAspectRatio 的变换，很可能只朝一个方向生效。2026-08-01 实测：`CGPDFPage.getDrawingTransform` 只把页面**缩小**以塞进目标矩形、**从不放大**——喂 2048×1152 的矩形，一页 960×540 的 PDF 会 1:1 居中绘制、四周大片留白，**不报错、不返回失败、图也确实产出了**。危险的是 base case 恰好把它盖住：只要样张尺寸都 ≥ 目标尺寸，缩小路径生效，一切正常。判据是问一句 *如果输入比目标小，会怎样？*，并让 fixture **同时含大于和小于目标的输入**。断言也要跟上：纯尺寸断言过不了这一关（留白的图尺寸也是对的），得断言内容非空白。详见 [跨层契约 · 原生二进制的契约边界与系统 API 的单向自适应](../backend/contracts.md)。

## 修复静默失败后的必查项

> **修好一个「没反应」，往往会让某个误操作第一次产生真实后果。**

M4 的实例：阶段轨道有 10 个点位横贯顶栏、单击即重跑。修复前误触无害（重跑压根不生效），修复后误触会作废该阶段及全部下游产物、重新调用付费 API。用户随即反馈「不知道在哪操作后会回退到上一阶段」。

所以每次修复后追问一句：**这个操作现在生效了，那误触它的代价是什么？** 代价高就要加确认、缩小点击区域，或提高触发门槛。
